# Instruções do projeto ChatGPT — pesquisa, arquitetura e execução

Repositório: https://github.com/heavydevs/plan-and-execute
Branch exclusiva: `checkpoint/plano1-estudo-provider-switch-20261028`

Execute **um ciclo completo da primeira task de desenvolvimento pendente** do plano ativo: pesquisa → decisão arquitetural → implementação/revisão → testes automatizados → revisão independente real (quando exigida) → gate final → commit/push. Não pare após produzir somente pesquisa nem avance à task seguinte enquanto a selecionada estiver incompleta.

## COMANDO `próximo` em novo chat — EXECUTAR revisão independente, não apenas buscar um provedor

Ao receber `próximo` numa **nova conversa deste Projeto ChatGPT**, conferir no GitHub o `HEAD` da branch e o primeiro `pending` do `manifest.json`. Se for a 015 e o gate depender de reviewer/receipt, **a própria nova conversa deve revisar de forma independente o código atual** antes de tentar Codex, Copilot ou Qwen: seguir [HANDOFF_REVISAO_015_NOVO_CHAT.md](HANDOFF_REVISAO_015_NOVO_CHAT.md). Ler especificação, decisões de arquitetura, implementação e testes; **não consultar chats anteriores, pareceres, outcomes ou outros pareceres de IA** antes de registrar um primeiro parecer com hashes, evidências e findings reproduzíveis. Publicar parecer na mesma branch, corrigir achados e executar testes/gates. Se alterar código, pedir **outra** revisão realmente independente dos hashes novos. Em conversa que já implementou, não chamar de review independente. Uma nova conversa prova separação operacional, **não automaticamente** modelo max, esforço ou session ID autenticados do gate — registrar só metadados efetivamente conhecidos.

## REGRA PRIORITÁRIA — Se reprovou, corrigir automaticamente

**Nunca pare a task apenas porque um teste, CI, code review ou gate final foi reprovado.** Continue na mesma sessão e **sem pedir nova confirmação**: leia os logs/artefatos do SHA exato, classifique a causa, reproduza e corrija o problema, teste a correção de forma focal e repita as validações completas. Se houver várias falhas, deixe a suíte chegar ao fim, consolide todas antes de corrigir e evite rodar tudo a cada mudança isolada. Repita o ciclo **falhou → corrigiu → testou → revalidou** até os gates passarem ou existir bloqueio externo comprovado.

- **Teste/código ou achado critical/high:** corrija a causa raiz com regressão negativa/positiva. Em mudança após review, solicite outro review real dos hashes finais; não reaproveite sessão antiga.
- **Gate por recibo, sessão ou hash ausente:** execute o pré-requisito verdadeiro e gere as evidências reais; nunca crie aprovação, log, teste, reviewer ou recibo inventado, nem altere o validador para ignorar a falha. Na 015, `P1_015` falha por falta de `015-receipt.json`: os testes passaram, mas a revisão externa max-tier autenticada e identificada por sessão ainda é necessária.
- **Infra, autorização ou créditos:** faça reparos seguros já autorizados; se depender de licença, política da organização, credencial ou custo não autorizado, documente o bloqueio e a ação exata necessária, preserve `pending` e **não** avance de task. Não faça loop de chamadas pagas nem prometa execução em segundo plano.

Procedimento completo e critérios de parada: [`guia_de_pesquisa_execucao_tasks.md`](../../guia_de_pesquisa_execucao_tasks.md#ciclo-obrigatório-de-autocorreção-após-reprovação) e [`PLAYBOOK.md`](PLAYBOOK.md#mandatory-automatic-correction-loop-on-failure). Só termine com `completed` depois dos gates originais, evidence packet e commit/push confirmados.

1. Antes de agir, leia o `AGENTS.md` da raiz, o `guia_de_pesquisa_execucao_tasks.md` e o roteador `.ai-work/chatgpt-executor/ENTRYPOINT.md`. Confirme branch, HEAD remoto, task inicial pendente do manifest, dependências, escopo, checklist de pesquisa e de execução e evidências existentes. **A task 015 tem pesquisa pronta, execução ainda pendente**: retome a execução, sem começar pela pesquisa 020.
2. Se a pesquisa da task escolhida estiver faltando ou desatualizada, estude o código e pesquise profundamente fontes oficiais, livros, artigos, estudos, benchmarks e alternativas. Salve relatório individual com referências, arquitetura adotada, segurança, performance, compatibilidade, orçamento de tokens e testes adversariais. Vincule o relatório à task e marque a pesquisa somente após validação e commit/push.
3. Implemente a task com base no relatório, corrigindo a arquitetura só quando houver divergência material demonstrável. Preserve contratos, status e dependências e mantenha a menor alteração necessária. Use GitHub connector com CAS para commits; se não houver checkout local, utilize GitHub Actions para testes reais sobre o SHA exato.
4. Execute todos os checks declarados. Deixe cada suíte chegar ao fim quando possível, consolide falhas e logs individualizados, corrija as falhas focais, e só então reexecute os gates completos. Não confunda testes do executor com testes da task.
5. **Primeiro, quando for novo chat com `próximo`, realizar a revisão cega nesta própria sessão** conforme o handoff; não dizer somente “não tenho Codex/Copilot”. Depois conferir o gate formal com modelo/effort/sessão/hash autênticos; `review_dispatch.py` ou provedor alternativo autorizado pode suprir esta etapa, não a inspeção inicial. Se os metadados do ChatGPT Web não são comprováveis, documentar limitação do gate sem reetiquetar o revisor nem criar recibo fictício. Nunca aprovar código recém alterado pela mesma conversa revisora.
6. Só quando o `check_delivery.py` original e validações finais passarem, registre recibo/outcome, conclua checkpoints pela autoridade do plano, marque execução no guia, faça commit/push na branch e confira o remoto. Sem review, credencial, ferramenta ou gate válido, mantenha a task pendente e registre bloqueio verificável; não fabrique evidências.
7. Não altere `main`, não use force-push, não inicie outra task na mesma execução e não faça perguntas de confirmação desnecessárias. Reaproveite estudos existentes, use leitura incremental, evite pagar por inferência desnecessária e reporte limites/custos potenciais.

Ao finalizar, informe a task escolhida, relatório/arquitetura, implementações, testes, revisão, gate, commits publicados, bloqueios reais e a próxima task somente se a atual tiver sido efetivamente concluída.
