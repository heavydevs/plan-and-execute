## Deeper analysis and competing approaches

### 1. Design analysis

Claude Code is the harness while GLM is the backend. The route identity must include the configured endpoint/profile and actual model mapping. An opus alias that resolves to the same GLM backend as sonnet is not a stronger retry. Preserve role labels for user readability, but do not use them as capability evidence.

### 2. Design analysis

Per-process environment overlays are safer than editing the user global Claude configuration. Reference environment variable names, validate allowed endpoints and strip unrelated credentials from diagnostic exports. Separate authentication failures, endpoint incompatibility and quota exhaustion from coding-quality failures.

### 3. Design analysis

Coding-plan eligibility is a product contract, not interchangeable with pay-as-you-go API access. Do not silently switch billing modes when a plan quota ends. Quality, native effort and tool/schema compatibility need workload-specific evidence; marketing benchmark claims do not assign a reliable floor in this repository.

### 4. Design analysis

Use opt-in profile fixtures and a minimal negative test corpus to make support maintainable. When a profile cannot express the required effort or read-only role, skip it with a reason. Avoid a broad alias rewrite that changes every existing plan snapshot.

The analysis above is a repository design synthesis. The linked publications establish capabilities or bounded empirical observations, not this skill's future measured performance. Exact account behavior and installed-version compatibility remain implementation-time checks.

## Implementation instructions

1. Persist normalized host, backend, endpoint profile name, actual model ID and quota-pool identity without secret values.
2. Make thinking/effort translation conditional on the supported GLM model and harness version. Unknown native controls must not be treated as a higher capability tier.
3. Keep workload qualification separate from generic tier mapping; do not inherit maximum Claude capability for a GLM profile.
4. Store API rates, subscription credit multipliers and cache economics in separate dated fields with null for unknowns. Refresh metadata without changing in-progress routes.
5. Inject configured environment references per child process and avoid editing the user's global Claude settings as an installation side effect.
6. Include endpoint/profile and resolved backend model in GLM route identity; collapse duplicate alias rungs.
7. Apply profile environment overlays only to child processes and never modify user-global settings.
8. Keep Coding Plan eligibility, quota and PAYG billing as separate explicit capabilities.

## Acceptance and counterexamples

- An Opus alias mapped to GLM retains backend=GLM in route, telemetry and cooldown identity.
- Unknown/unsupported effort is rejected or mapped by an explicit tested rule, never silently upgraded.
- Two profiles using the same host but different quota pools do not contaminate one another.
- Secret values are absent from show/config receipts, logs and handoff packets.
- Version1 configuration snapshots preserve their original behavior.
- Opus and Sonnet aliases mapped to one GLM model do not count as a capability increase.
- Child profile settings cannot leak into another provider process.
- Coding Plan quota exhaustion cannot enable an API-paid route implicitly.
- Unknown native effort support causes an explicit skip rather than guessed equivalence.
